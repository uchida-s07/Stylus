## 1. 要求（Why）

- 関連する要求: G-1, J-1（あわせて、vision「利害関係者」の管理者の期待「費用をかけずに作って運用し続けられる」）
- 解決したい課題: ご飯・車・お金の機能を載せる土台が無い。土台とは、家族だけが入れること、ログインが続くこと、権限、PWA、API と DB、無料での運用を指す。J-1 の「一度ログインすれば、次からは開くだけで使い続けられる」を実現し、あとの機能の spec が共通の仕組みの上に作れるようにする
- 対象ユーザー: 家族4人（母・父・息子2人）と管理者（せいご）
- 成功の判断基準:
  1. 家族4人が各自の Android スマホで Google ログインし、端末のホーム画面のアイコンから開ける
  2. 最後に開いてから7日以内なら、再ログインを求められない。求められても、Google のボタンから本人だけで戻れる
  3. 家族以外の Google アカウントでは入れない
  4. 本番・開発の両方が費用0円で動き、Supabase が休止しない
  5. 最初の機能の spec を、この土台の上にすぐ作り始められる

### 要件の変更後の姿

#### AUTH-F-001 管理者が家族を事前に登録できる（新規）

- **概要**: 管理者が、家族一人ひとりのメールアドレス（Google アカウント）・表示名・立場（親・料理担当）・ロール（管理者）を登録する。登録された人だけが家族として扱われる。登録する画面は作らず、管理者が決められた手順で登録する
- **事前条件**: 管理者が本番・開発の Supabase を操作できる
- **正常フロー**: 管理者が家族のメールアドレスで利用者を作る → その利用者に結びつけて、表示名・立場・ロールを登録する → その家族が Google でログインすると、本人として扱われる
- **例外・バリデーション**:
  - 入力が空・欠けている: メールアドレスか表示名が空（表示名は空白だけも含む）なら、登録を止める
  - 対象外・想定外: 同じメールアドレスを2回登録しようとしたら、2件目を止める。大文字を含むメールアドレスは登録を止める（小文字で登録し直す）。利用者は作られたが家族の登録（表示名・立場）が無い人は、ログインしても家族として扱わない（AUTH-F-002 の未登録と同じ扱い）
  - 処理に失敗: 登録の途中で失敗して片方だけが残った場合は、入れない側に倒れる。利用者だけが残ったときは上の「家族の登録が無い」扱い、家族の登録だけが残ったときはサインアップ無効で弾かれ、どちらも AUTH-F-002 の未登録と同じ表示になる。管理者は手順をやり直す
- **受入基準**:
  - AC-1: Given 管理者が yuriko@example.com を表示名「母」・立場「親」「料理担当」・ロールなしで登録済み / When その Google アカウントでログインし、自分の情報を API に問い合わせる / Then 表示名「母」、立場「親」「料理担当」、ロールなしが返る
  - AC-2: 〔例外：対象外の入力〕Given yuriko@example.com が登録済み / When 同じメールアドレスでもう一度家族を登録する / Then 登録は拒否され、そのメールアドレスの家族は1人のまま
  - AC-3: 〔例外：入力が空〕Given 登録済みの家族がいない / When 表示名を空（""）、または空白だけ（"　"）にして家族を登録する / Then どちらも登録は拒否され、家族は0人のまま
  - AC-4: 〔例外：入力が空〕Given 登録済みの家族がいない / When メールアドレスを空にして家族を登録する / Then 登録は拒否され、家族は0人のまま
  - AC-5: 〔例外：対象外の入力〕Given 登録済みの家族がいない / When メールアドレスを Yuriko@example.com（大文字を含む）にして家族を登録する / Then 登録は拒否され、家族は0人のまま
- **対応する要求**: G-1, J-1

#### AUTH-F-002 登録された家族が Google でログインできる（新規）

- **概要**: ログイン画面の「Google でログイン」から Google アカウントで認証し、登録済みの家族ならアプリのホームに入る。登録されていない Google アカウントでは入れない
- **事前条件**: AUTH-F-001 で本人が登録されている。この端末でログインしていない
- **正常フロー**: アプリを開く → ログイン画面が出る → 「Google でログイン」を押す → Google の画面でアカウントを選ぶ → アプリに戻る → アプリのホームに自分の表示名が出る
- **例外・バリデーション**:
  - 入力が空・欠けている: Google の画面でアカウントを選ばずに戻った（キャンセル）ときは、ログイン画面に戻す。メッセージは出さない
  - 対象外・想定外: 登録されていない Google アカウントのときは、ホームに入れず「この Google アカウントは登録されていません。管理者に連絡してください。」と出し、ログインしていない状態に戻す。ログインしていない状態でホームなどの画面を直接開いたときは、ログイン画面を出す。ログイン済みでログイン画面を開いたときは、ホームを出す
  - 処理に失敗: Google・Supabase・通信のどれかで失敗したときは、「ログインできませんでした。時間をおいてもう一度お試しください。」と出し、ログイン画面に留める
- **受入基準**:
  - AC-1: Given 表示名「母」で登録済みの Google アカウント / When 「Google でログイン」からログインを終える / Then アプリのホームに「母」と表示される
  - AC-2: 〔例外：対象外の入力〕Given 登録されていない Google アカウント / When 「Google でログイン」を押し、Google の画面でそのアカウントを選んでアプリに戻る / Then アプリのホームは出ず「この Google アカウントは登録されていません。管理者に連絡してください。」と表示される
  - AC-3: 〔例外：処理に失敗〕Given ログインの途中で認証に失敗する / When 「Google でログイン」からログインする / Then 「ログインできませんでした。時間をおいてもう一度お試しください。」と表示され、ログイン画面のまま
  - AC-4: 〔例外：対象外の入力〕Given この端末でログインしていない / When アプリのホームの URL を直接開く / Then ログイン画面が出る
  - AC-5: 〔例外：対象外の入力〕Given この端末でログイン済み / When ログイン画面の URL を開く / Then アプリのホームが出る
  - AC-6: 〔例外：対象外の入力〕Given 登録されていない Google アカウントで弾かれた直後 / When アプリを開き直す / Then ログイン画面が出る
  - AC-7: 〔例外：入力が空〕Given 「Google でログイン」を押して Google の画面が出ている / When Google の画面でキャンセルしてアプリに戻る / Then ログイン画面のままで、メッセージは出ない
- **対応する要求**: G-1, J-1

#### AUTH-F-003 ログインしたまま使い続けられる（新規）

- **概要**: 一度ログインすると、ログアウトするまで、アプリを開くたびにログイン画面を経ずにアプリのホームに入れる。少なくとも、最後に開いてから7日以内なら再ログインを求めない
- **事前条件**: AUTH-F-002 でこの端末からログイン済み
- **正常フロー**: アプリを開く → 端末に残っているログイン状態を読む → アクセストークンの期限が切れていれば自動で更新する → アプリのホームが出る
- **例外・バリデーション**:
  - 入力が空・欠けている: 端末にログイン状態が残っていない（初めて開いた、ブラウザのデータを消した）ときは、ログイン画面を出す
  - 対象外・想定外: ログイン状態が無効になっている（長く開かずに失効した、取り消された）ときは、ログイン画面を出す。再ログインは「Google でログイン」から本人だけでできる。家族の登録から外された人は、AUTH-F-002 の未登録と同じ表示にする。使っている最中にアクセストークンの期限が切れたときは、自動で更新して操作を続ける（利用者には見せない）
  - 処理に失敗: 通信できずに更新できないときは、ログイン状態を消さず「通信できません。電波の良いところでもう一度開いてください。」と出す。API やサーバーが失敗を返したとき（DB につながらないなど）も、ログイン状態を消さず「うまく読み込めませんでした。時間をおいてもう一度開いてください。」と出す
- **受入基準**:
  - AC-1: Given 最後に開いてから7日たち、アクセストークンの期限が切れている / When アプリを開く / Then ログイン画面を経ずにアプリのホームが出る
  - AC-2: 〔例外：対象外の入力〕Given 端末に残っているログイン状態が無効になっている / When アプリを開く / Then ログイン画面が出る
  - AC-3: 〔例外：処理に失敗〕Given アクセストークンの期限が切れていて、通信できない / When アプリを開く / Then 「通信できません。電波の良いところでもう一度開いてください。」と表示され、端末のログイン状態は残っている
  - AC-4: Given アプリを開いたまま、アクセストークンの期限（1時間）を過ぎた / When アプリのホームを再読み込みする（自分の情報を問い合わせる API が呼ばれる） / Then 再ログインを求められずに、アプリのホームに自分の表示名が出る
  - AC-5: Given AC-3 のあと通信が戻った / When アプリを開き直す / Then ログイン画面を経ずにアプリのホームが出る
  - AC-6: 〔例外：対象外の入力〕Given 端末にログイン状態が残っているが、家族の登録から外されている / When アプリを開く / Then 「この Google アカウントは登録されていません。管理者に連絡してください。」と表示される
  - AC-7: 〔例外：処理に失敗〕Given この端末でログイン済みで、自分の情報を問い合わせる API が 500 を返す / When アプリを開く / Then 「うまく読み込めませんでした。時間をおいてもう一度開いてください。」と表示され、端末のログイン状態は残っている
- **対応する要求**: J-1

#### AUTH-F-004 ログアウトできる（新規）

- **概要**: ログアウトすると、この端末のログイン状態を消し、ログイン画面に戻る。ほかの端末のログイン状態には触れない
- **事前条件**: AUTH-F-002 でこの端末からログイン済み
- **正常フロー**: 「ログアウト」を押す → 「ログアウトしますか？」の確認で「ログアウト」を選ぶ → この端末のログイン状態が消える → ログイン画面が出る
- **例外・バリデーション**:
  - 入力が空・欠けている: 確認で「キャンセル」を選んだら、何もせず元の画面に戻る
  - 対象外・想定外: ログイン状態がすでに無効になっているときも、同じようにログイン画面を出す
  - 処理に失敗: 通信できずにサーバー側の取り消しができないときも、この端末のログイン状態は消してログイン画面を出す
- **受入基準**:
  - AC-1: Given この端末でログイン済み / When 「ログアウト」を押し、確認で「ログアウト」を選ぶ / Then ログイン画面が出て、端末に保存されたログイン状態が消えている
  - AC-2: 〔例外：入力が空〕Given この端末でログイン済み / When 「ログアウト」を押し、確認で「キャンセル」を選ぶ / Then 元の画面のままで、ログイン状態も残っている
  - AC-3: 〔例外：処理に失敗〕Given この端末でログイン済みで、通信できない / When 「ログアウト」を押し、確認で「ログアウト」を選ぶ / Then ログイン画面が出て、端末に保存されたログイン状態が消えている
  - AC-4: Given 端末 A と端末 B でログイン済み / When 端末 A でログアウトする / Then 端末 B のログイン状態は取り消されない（ほかの端末のログイン状態を取り消す要求を送らない）
- **対応する要求**: J-1

#### APP-F-001 端末のホーム画面に追加して、アプリとして開ける（新規）

- **概要**: Android の Chrome でアプリを端末のホーム画面に追加（インストール）でき、そのアイコンから開くと、アドレスバーの無い画面でアプリが開く。追加しなくても、スマホ・PC のブラウザでそのまま使える
- **事前条件**: 本番（またはプレビュー）の URL を Chrome で開ける
- **正常フロー**: Chrome でアプリを開く → メニューの「ホーム画面に追加」（「アプリをインストール」）を選ぶ → 端末のホーム画面に「Stylus」のアイコンができる → アイコンをタップする → アドレスバーの無い画面でアプリが開く（ログイン済みならアプリのホーム）
- **例外・バリデーション**:
  - 入力が空・欠けている: 該当なし（利用者が入力するものが無い）
  - 対象外・想定外: 端末のホーム画面への追加に対応していないブラウザでは追加できないが、ブラウザのまま使える。新しい版を公開した後に古い版が端末に残っているときは、新しい版に切り替える
  - 処理に失敗: 通信できないときにアイコンから開いたら、真っ白な画面にせず、端末に保存済みの画面を出して「通信できません。電波の良いところでもう一度開いてください。」と出す
- **受入基準**:
  - AC-1: Given 本番用にビルドしたフロント / When 出力された Web アプリマニフェストを読む / Then 名前が「Stylus」、表示モードが standalone（アドレスバーなし）、`start_url` がアプリのホーム、192px と 512px のアイコンが入っている
  - AC-2: Given 本番用にビルドしたフロント / When 出力されたファイルを調べる / Then Service Worker があり、アプリの画面（HTML・JS・CSS）を端末に保存する対象にしている
  - AC-3: 〔例外：処理に失敗〕Given この端末でログイン済みでアクセストークンは期限内、画面は読み込めたが通信できない（API・Supabase への要求がネットワークエラーになる） / When アプリを開く / Then 「通信できません。電波の良いところでもう一度開いてください。」と表示される
- **対応する要求**: J-1

#### COMMON-N-001 API はアクセストークンを検証し、家族として登録された人だけを通す（新規）

- **概要**: 【セキュリティ】API は、CORS の事前確認を除くすべての要求で、`Authorization: Bearer` の Supabase のアクセストークン（JWT）を検証する。Cookie は使わない。トークンが無い・形式が違う・署名が正しくない・期限切れなら 401、トークンは有効でも家族として登録されていない人なら 403 を返す。有効期限は、アクセストークンが1時間、ログイン状態（リフレッシュトークン）には期限を設けない（どちらも Supabase の既定。AUTH-F-003 の7日は下限の約束）
- **測り方**: API の自動テスト
- **受入基準**:
  - AC-1: Given `Authorization` ヘッダーが無い / When 自分の情報を問い合わせる API を呼ぶ / Then 401 が返る
  - AC-2: Given 署名が正しくないトークン / When 同じ API を呼ぶ / Then 401 が返る
  - AC-3: Given 期限切れのトークン / When 同じ API を呼ぶ / Then 401 が返る
  - AC-4: Given 有効なトークンだが、家族として登録されていない利用者 / When 同じ API を呼ぶ / Then 403 が返る
  - AC-5: Given 家族として登録された利用者の有効なトークン / When 同じ API を呼ぶ / Then 200 と本人の情報が返る
- **対応する要求**: G-1

#### COMMON-N-002 権限は固定で、判定は API で行う（新規）

- **概要**: 【セキュリティ】権限は、ロール「管理者」（せいご）と、立場「親」（父・母）「料理担当」（現在は母）で表す。家族の登録時に決め、アプリの中では変えない（AUTH-F-001）。ロールや立場が要る操作の可否は API が判定し、足りなければ 403 を返す。フロントのボタンの出し分けは見た目のためだけで、判定には使わない。各機能の spec は、どの操作にどのロール・立場が要るかをこの仕組みで定める
- **測り方**: API の自動テスト
- **受入基準**:
  - AC-1: Given 料理担当だけに許す判定を付けたルート（テストの中だけで組み立てる）と、料理担当ではない家族（息子）のトークン / When そのルートを呼ぶ / Then 403 が返る
  - AC-2: Given AC-1 と同じルートと、料理担当の家族（母）のトークン / When そのルートを呼ぶ / Then 403 にならずに処理される
  - AC-3: Given 管理者だけに許す判定を付けたルート（テストの中だけで組み立てる）と、管理者ではない家族（母）のトークン / When そのルートを呼ぶ / Then 403 が返る
  - AC-4: Given AC-3 と同じルートと、管理者（せいご）のトークン / When そのルートを呼ぶ / Then 403 にならずに処理される
- **対応する要求**: G-1

#### COMMON-N-003 Supabase の Data API から直接読み書きできない（新規）

- **概要**: 【セキュリティ】Supabase の公開キーや利用者のアクセストークンを使っても、Data API（PostgREST）経由ではアプリのデータを読むことも書くこともできない。データの読み書きはすべて Hono API を通す
- **測り方**: マイグレーションの自動テスト。あわせて、公開キーで Data API を呼んでアプリのデータを読めない・書けないことを、本番・開発の両方でリリース前に手で確かめる
- **受入基準**:
  - AC-1: Given すべてのマイグレーションを当てた DB / When public スキーマのテーブルを調べる / Then すべてのテーブルで RLS が有効で、ポリシーは1つも無い
- **対応する要求**: G-1

#### COMMON-N-004 秘密情報は決めた場所にだけ置き、フロントの成果物に含めない（新規）

- **概要**: 【セキュリティ】秘密情報の置き場所を次に限る。どれもリポジトリに入れず、ローカル開発用の値は git の管理外のファイルに置く。フロントには秘密情報を渡さない。フロントに渡すのは、Supabase の URL と公開キー（`sb_publishable_`）、API の URL、Sentry の DSN（どれも公開してよい値）だけ。Supabase のキーは新しい形式（`sb_publishable_` / `sb_secret_`）だけを使い、古い形式（JWT の anon / service_role キー）は使わない
  - サービスロールキー（`sb_secret_`）：Workers の secret
  - DB の接続情報：Workers の secret（Hyperdrive を使うならその設定）。例外として、マイグレーション用は GitHub Actions の secret にも置く
  - Cloudflare の API トークン（デプロイ用）：GitHub Actions の secret
  - Google OAuth のクライアントシークレット：Supabase の管理画面（Auth の設定）
- **測り方**: 自動テストでリポジトリの追跡ファイルを検査する。あわせて CI で、フロントのビルド成果物に秘密情報の値の形（`sb_secret_` の後ろにキーの文字が続くもの、`postgres://`・`postgresql://` の後ろにユーザーとパスワードが続く接続文字列）が無いことを検査する。成果物では値の形で探すのは、ライブラリ（supabase-js）がキーの種類の見分けに `sb_secret_` の文字列そのものを持つため
- **受入基準**:
  - AC-1: Given git で追跡しているファイル（`docs/` と、検査する形を定義したファイル自身を除く） / When 秘密情報の形（`sb_secret_`、`postgres://`、`postgresql://`）を探す / Then 1件も見つからない
- **対応する要求**: G-1

#### COMMON-N-005 CORS で許可するのは決めたオリジンだけ（新規）

- **概要**: 【セキュリティ】本番の API（`stylus-api`）が許可するのは、本番のフロントのオリジン（`https://stylus-family.pages.dev`）だけ。開発の API（`stylus-api-dev`）が許可するのは、Pages のプレビュー URL（`https://<任意の1階層>.stylus-family.pages.dev`）と、ローカル開発サーバーのオリジン（`http://localhost:5173`）だけ
- **測り方**: API の自動テスト（本番用・開発用の設定それぞれで）
- **受入基準**:
  - AC-1: Given 本番用の設定 / When `https://stylus-family.pages.dev` から CORS の事前確認を送る / Then `Access-Control-Allow-Origin: https://stylus-family.pages.dev` が返る
  - AC-2: Given 本番用の設定 / When `https://example.com`、`https://stylus.pages.dev`（他人のサイト）、`http://localhost:5173`、`https://spec-001-foundation.stylus-family.pages.dev` から事前確認を送る / Then どれも許可されない（`Access-Control-Allow-Origin` が返らない）
  - AC-3: Given 開発用の設定 / When `https://spec-001-foundation.stylus-family.pages.dev`、`https://develop.stylus-family.pages.dev`、`http://localhost:5173` から事前確認を送る / Then どれも許可される
  - AC-4: Given 開発用の設定 / When `https://example.com` から事前確認を送る / Then 許可されない
  - AC-5: Given 開発用の設定 / When よく似たオリジン `https://stylus-family.pages.dev.example.com`、`https://xstylus-family.pages.dev`、`https://other.pages.dev`、`http://develop.stylus-family.pages.dev`、`https://a.b.stylus-family.pages.dev` から事前確認を送る / Then どれも許可されない
- **対応する要求**: G-1

#### COMMON-N-006 Supabase が休止しない（新規）

- **概要**: 【可用性】Supabase の無料プランは7日間アクセスが無いと休止するため、Workers の Cron で本番・開発の両方の Supabase に毎日1回アクセスする（手段は問わない）。アクセスに失敗したら Sentry に送る（翌日の実行で取り返せるので、その場で再試行はしない）
- **測り方**: Workers のダッシュボードで Cron が毎日成功していること、Supabase が休止していないことを運用で確かめる。Cron の処理は自動テスト
- **受入基準**:
  - AC-1: Given Cron の処理 / When 実行する / Then Supabase への問い合わせが1回送られ、成功の応答を受け取る
  - AC-2: Given Supabase への問い合わせが失敗する / When Cron の処理を実行する / Then エラーが Sentry に1回送られる
- **対応する要求**: G-1

#### COMMON-N-007 API の CPU 時間を1リクエスト 10ms 以内に収める（新規）

- **概要**: 【性能】Workers の無料プランの上限に合わせ、API の1リクエストあたりの CPU 時間を 10ms 以内に収める。重い処理を Workers でしない
- **測り方**: リリース前に、主な API を呼んだときの CPU 時間を Workers のダッシュボード（または `wrangler tail`）で確かめる（目安）
- **受入基準**:
  - 自動テストでは確かめない（測り方のとおり、リリース前に確かめる）
- **対応する要求**: G-1

#### COMMON-N-008 スマホ優先で、PC でも崩れない（新規）

- **概要**: 【ユーザビリティ】幅 360px のスマホの縦持ちを基準に作り、幅 1280px の PC でも崩れない（横スクロールが出ず、すべての操作ができる）。父・母が素早い操作や細かい操作をしなくて済むよう、押せる部分は 44×44px 以上にする
- **測り方**: 幅 360px と 1280px で、この spec で作る画面（ログイン画面・アプリのホーム）を表示して確かめる（手動）
- **受入基準**:
  - 自動テストでは確かめない（測り方のとおり、手動で確かめる）
- **対応する要求**: G-1

#### COMMON-N-009 日付の区切りは日本時間に揃える（新規）

- **概要**: 【ユーザビリティ】画面・API・DB で日付を扱うときは、日本時間（UTC+9）の0時で区切る。Workers の Cron は UTC で動くので、Cron の処理でも日付は日本時間で求める。日付の求め方は `packages/` の共通のルール1つにまとめる
- **測り方**: 共通のルールの自動テスト
- **受入基準**:
  - AC-1: Given 日時 2026-10-01T15:00:00Z（日本時間 10月2日 0:00） / When 日付を求める / Then 2026-10-02 になる
  - AC-2: Given 日時 2026-10-01T14:59:59Z（日本時間 10月1日 23:59:59） / When 日付を求める / Then 2026-10-01 になる
- **対応する要求**: G-1

#### COMMON-N-010 フロントから API の実行コードを import しない。test と lint を CI で回す（新規）

- **概要**: 【保守性】`apps/web` は `apps/api` の実行コードを import しない（`import type` だけ許す）。共有するもの（型・スキーマ・ルール）は `packages/` に置く。`develop`・`main` への PR ごとに、GitHub Actions で `pnpm test` と `pnpm lint` を回す。失敗した PR はマージしない（ブランチ保護が使えないため運用で守る）
- **測り方**: lint のルールの自動テスト。PR ごとに GitHub Actions が走り、結果が PR に出ることは、最初の PR で手で確かめる
- **受入基準**:
  - AC-1: Given `apps/web` のファイルに `apps/api` の実行コードを import する行がある / When `pnpm lint` を実行する / Then エラーになる
  - AC-2: Given `apps/web` のファイルに `apps/api` からの `import type` の行だけがある / When `pnpm lint` を実行する / Then その行ではエラーにならない
- **対応する要求**: G-1

#### COMMON-N-011 予期しないエラーを Sentry で拾う（新規）

- **概要**: 【保守性】API とフロントで起きた予期しないエラー（処理で捕まえていない例外）を Sentry（無料の Developer プラン）に送る。本番と開発は分けて見られるようにする。送る内容にアクセストークンや秘密情報を含めない
- **測り方**: API の自動テスト。あわせて、開発環境でわざとエラーを起こして Sentry に届くかを手動で確かめる
- **受入基準**:
  - AC-1: Given API の処理が予期しない例外を投げる / When その API を呼ぶ / Then 500 が返り、Sentry への送信が1回行われる
  - AC-2: Given `Authorization` ヘッダー付きの要求で予期しない例外が起きる / When Sentry に送る内容を作る / Then 内容にアクセストークンが含まれない
- **対応する要求**: G-1

### スコープ外

| 項目 | 区分 | 理由 |
|------|-----|------|
| ご飯・車・お金の各機能（J-2〜J-10） | 後回し | 機能ごとの spec で作る。作る順番はまだ決めない |
| 家族の登録・立場を変える画面 | やらない | vision の非目標（家族の役割をアプリ上で変える）。4人固定のため |
| 管理者だけの機能 | 後回し | ロールは用意するが、今は機能が無い |
| バックアップ | 後回し | 取れなくても困らない。取るなら GitHub Actions で dump → R2 など |
| 通信が無いときにデータを見る（オフライン対応） | 後回し | 家族の困りごとに出てこない |
| iPhone（Safari）でのログインの維持 | 後回し | 4人とも Android。iPhone に替えたら考え直す（Safari は7日間開かないと保存領域を消す） |
| Web プッシュの仕組み（購読の登録・解除、送信）と検証 V-4 | 後回し | 使うのは「作れない日」の通知だけなので、作れない日の spec でまとめて作る（2026-09-27 オーナー決定） |

現時点でアプリのコードは無い（リポジトリは文書だけ）。以下はすべて新規。構成の方針・理由は design.md に書く。

### API

- 新規：`GET /me` … 自分の表示名・立場・ロールを返す。401 / 403 は COMMON-N-001 のとおり（AUTH-F-001、AUTH-F-002）
