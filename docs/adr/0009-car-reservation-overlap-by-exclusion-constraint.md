# ADR-0009: 車の予約の時間の重なりを、Postgres の排他制約（btree_gist）で防ぐ

- 状態: 採用
- 日付: 2026-10-11
- 関連する spec: specs/003-car
- 置き換えた ADR: —
- 置き換えられた ADR: —

## 背景

車（spec 003）では、同じ車で時間が重なる予約を入れられないようにする（CAR-F-004）。後から入れようとした予約を止め、先に入れた予約を優先する。2人の家族がほぼ同時に予約を送ったときも、重なる予約が2件とも入ってはいけない（CAR-F-004/AC-6）。

API は Cloudflare Workers で動き、DB へは Hyperdrive 経由でつなぐ（ADR-0006）。Workers Free はリクエストあたり CPU 10ms で、DB との往復は少ないほうがよい。スキーマは Drizzle で書き、マイグレーションは Drizzle Kit で作る。テストの DB は PGlite。

## 決定

- `car_reservations` に排他制約を付ける：`EXCLUDE USING gist (car_id WITH =, tstzrange(starts_at, ends_at, '[)') WITH &&)`（制約の名前は `car_reservations_no_overlap`）
  - `[)`（開始を含み終了を含まない）なので、12:00 に終わる予約と 12:00 に始まる予約は重ならない
  - `car_id` の `=` を gist で扱うために拡張 `btree_gist` を使う。Supabase では `extensions` スキーマに入れる（`create extension if not exists btree_gist with schema extensions`）。マイグレーションの接続から有効にでき、管理画面での手当ては要らなかった（spec 003 の V-2）
- 排他制約は Drizzle のスキーマでは書けないので、Drizzle Kit が生成したマイグレーション（0004）に手で SQL を足す。スキーマのファイルには、制約の名前と中身をコメントで残す
- API は重なりを事前に調べずに挿入・更新し、制約違反（`23P01`）を 409 `overlap` にする。重なった相手の予約（表示名・開始・終了）は、違反を受けた後に1回だけ問い合わせて知らせに付ける
- テスト（PGlite）では、PGlite の拡張 `btree_gist` を読み込み、拡張の前に `extensions` スキーマを作る（spec 003 の V-1）

## 検討した代替案

| 案 | 採らなかった理由 |
|----|----------------|
| 重なりを API で調べてから挿入する（`SELECT` → `INSERT`） | 同時に送られた2つの予約が、両方とも「重ならない」と判定されて入る |
| API で判定し、車ごとに `pg_advisory_xact_lock` で直列にする | 排他制約より込み入り、DB に直接書き込んだときは守られない。排他制約が使えなかったときの代替として残した（使えたので採らなかった） |
| 開始・終了を `tstzrange` の1列で持つ | Drizzle が範囲型を素直に扱えず、画面との受け渡しも2つの日時のほうが分かりやすい。制約の中でだけ範囲にすれば足りる |

## 結果（トレードオフ）

- 良くなること: 同時の予約でも、重なる予約は DB が必ず止める。重ならない普通の登録では余分な問い合わせが無い（重なったときだけ1回増える）
- 悪くなること・受け入れたリスク: 拡張 `btree_gist` に頼る（本番の Supabase でも同じ手順で有効にする）。制約が Drizzle のスキーマの外（手で足した SQL）にあり、スキーマのファイルだけを見ても分からない（コメントで補う）。取り消した予約を状態として残すことにしたら、部分制約に変える必要がある（今は取り消しで行を消す）
