# ADR-0003: Google ログイン＋事前登録にし、家族の照合は members の表で行う

- 状態: 採用
- 日付: 2026-09-27
- 関連する spec: specs/001-foundation
- 置き換えた ADR: —
- 置き換えられた ADR: —

## 背景

利用者は家族4人で固定され、4人とも Google アカウントを持っている。家族以外は使えないようにし、一度ログインしたら使い続けられるようにしたい。独自ドメインを持たないので、ログインのためのメールを自前で送る仕組み（独自 SMTP）は用意しにくい。各機能のデータは「家族の誰のものか」を持つ必要がある。

## 決定

- ログインは Supabase Auth の Google ログインだけにする。Google 以外のログイン方法は無効にする
- 一般公開のサインアップは無効にする。管理者が Supabase の管理画面で家族の利用者を作り（メールを送らない方法で）、`members` の表に表示名・ロール・立場を登録する。手順は `docs/architecture.md` の「家族の登録の仕方」
- `members` は Auth の利用者とは別の ID（uuid）を主キーに持ち、Auth の利用者 ID を `auth_user_id` に入れる。家族の登録のときに `auth_user_id` まで埋める
- API はトークンの `sub` で `members.auth_user_id` を探し、見つからなければ 403 `not_a_member` を返す
- 実物での確認（V-1、2026-09-27、開発環境）：サインアップ無効のまま、管理画面で作った利用者が Google でログインでき、利用者は増えずに同じ利用者に Google の ID が加わった。ログイン後も `app_metadata.provider` は `email` のまま残る

## 検討した代替案

| 案 | 採らなかった理由 |
|----|----------------|
| メール・パスワード、メールのリンクでのログイン | ログインのメールを送る仕組みが要り、独自ドメインなしの制約と合わない。パスワードの処理を持つと Workers の CPU 時間にも響く |
| サインアップを許可し、`members` に無い人は API が 403 にする（V-1 の代替） | V-1 が合格したので不要。家族以外もアカウントを作れてしまう。`auth_user_id` を NULL 可にして `email` を持っておき、この方式に切り替えても表を変えずに済むようにはしてある |
| 初回ログインのときにトークンのメールアドレスで `members` と紐づける | 管理画面で作った利用者は `app_metadata.provider` が `email` のまま残るため、Google でログインしたことを確かめる条件が立てにくく、初回ログインが 403 になる。登録のときに `auth_user_id` まで埋めれば、照合は `sub` だけで済む |
| `members` の主キーを Auth の利用者 ID にする | V-1 の代替に切り替えると、ログイン前に行を作れなくなる。利用者を作り直すと、各機能のデータの持ち主が変わってしまう |
| 家族の情報を Auth の `app_metadata` に持つ | 各機能のテーブルから外部キーで参照できない。管理画面での編集も手間 |

## 結果（トレードオフ）

- 良くなること: メールの送信もパスワードの処理も要らない。家族以外は、サインアップ無効と `members` での照合の二重で止まる（開発では Google の同意画面を「テスト中」にしてテストユーザーを絞っており、三重になる）。家族の ID が Auth と切り離されているので、利用者を作り直してもデータの持ち主は変わらない
- 悪くなること・受け入れたリスク: 家族の登録は手作業で、メールアドレスを打ち間違えると0件のまま成功扱いで終わる（手順の中で結果を確かめる）。全員が Google アカウントに頼る。Google の同意画面を「テスト中」のまま使うと、同意から7日たつと同意画面がもう一度出ることがある（アプリのログイン状態は Supabase が持つので切れない）。本番でどうするかは本番の準備（T-25）で決める
