# ADR-0001: フロントエンドとバックエンドを完全に分ける

- 状態: 採用
- 日付: 2026-09-27
- 関連する spec: specs/001-foundation
- 置き換えた ADR: —
- 置き換えられた ADR: —

## 背景

家族4人（全員 Android）が使うアプリを、完全無料の範囲・独自ドメインなしで作る。今は Web（PWA）で配るが、将来ネイティブアプリへ移る可能性がある。画面とデータの読み書き・権限の判断をどこに置くかを、最初に決める必要があった。

## 決定

- フロントエンド（`apps/web`、Cloudflare Pages）とバックエンド API（`apps/api`、Hono・Cloudflare Workers）を別のアプリとして作り、別々に配置する
- データの読み書きはすべて API を通す。フロントが Supabase を直接使うのはログイン・ログアウト・セッション管理だけ（ADR-0004）
- API にはアクセストークンを `Authorization: Bearer` で送る。Cookie は使わない（ネイティブアプリからも同じ方式で呼べるように）
- 認可（権限の判断）は API で行う。フロントの表示の出し分けは見た目のためだけ
- 画面以外で共有するもの（型・Zod スキーマ・ルール）は `packages/` に置く。`apps/web` から `apps/api` の実行コードは import しない（`import type` だけ。ESLint で止める）

## 検討した代替案

| 案 | 採らなかった理由 |
|----|----------------|
| 画面とサーバーの処理を1つのアプリにまとめる | ネイティブアプリへ移るときに、画面と一体になったデータの読み書き・権限の判断を切り出し直すことになる。役割を分けたほうが、画面の不具合が権限の判断に響かず堅牢 |

## 結果（トレードオフ）

- 良くなること: ネイティブアプリへ移っても API と `packages/` をそのまま使える。権限の判断が API の1か所にまとまり、画面の作りに左右されない。フロントに秘密情報を置かずに済む
- 悪くなること・受け入れたリスク: 配置先が2つになり、CORS の設定（許可するオリジンの管理）が要る。DB のマイグレーション・API・フロントが別々に配信されるので、古い API やフロントが新しいスキーマで動く時間があり、列の削除や名前の変更は2回に分けて行う必要がある。Pages のプレビューは共通の開発用 API（`stylus-api-dev`）につなぐので、ブランチごとに API を分けられない
