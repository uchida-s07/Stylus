# ADR-0008: 状態の更新を、版つきの条件付き更新（楽観的な排他）で行う

- 状態: 採用
- 日付: 2026-10-04
- 関連する spec: specs/002-money
- 置き換えた ADR: —
- 置き換えられた ADR: —

## 背景

お金（spec 002）では、同じ請求を複数の家族が同時に操作しうる。「家庭」宛ての請求を父母が別々の端末で同時に「払った」にする、請求先が画面を開いている間に請求する側が金額を直す、などである。後から通った操作が先の操作を黙って上書きすると、記録が食い違う（MONEY-F-006/AC-4・AC-5）。

API は Cloudflare Workers で動き、DB へは Hyperdrive 経由でつなぐ（ADR-0006）。Workers Free はリクエストあたり CPU 10ms で、DB との往復は少ないほうがよい。今後の機能（車の予約の変更など）でも同じ問題が起きるので、そのときの前例になる。

## 決定

- 状態を持つ記録には `version`（整数）を持たせ、更新のたびに1増やす。画面は読んだときの `version` を付けて操作を送る
- 1件の操作は、判定（関係者・側・状態遷移）の後に、条件付きの更新を1文で行う：`UPDATE … SET …, version = version + 1 WHERE id = ? AND status = ? AND version = ?`。0行なら、開いた後に別の人が変えたということなので、409 `state_changed` を返す
- 更新と経過の追加は1つのトランザクションで行う
- 複数の記録をまとめて変える操作（まとめて払った）だけは、トランザクションの中で `SELECT … FOR UPDATE` で対象を読み、画面が送った `{ id, version }` の一覧と完全に一致するかを確かめてから更新する
- 画面は 409 を受けたら記録を取り直し、状態が見ていたときと同じなら「中身が変わりました」、違えば「状態が変わりました」と出し分ける
- 対象外（2026-10-11、specs/003-car で追記）: 次は版を持たない・見ない
  - 結果の値をそのまま送るだけで、遷移の規則と経過を持たない属性（車の名前・使う／使わない）。後勝ちでも最後に送った値になるだけで、記録が食い違わない
  - 本人だけが行い、経過を残さない記録の削除（車の予約の取り消し）。取り消したい意図は中身に左右されず、操作するのは本人だけなので、開いた後に本人がほかの端末で直していても取り消す

## 検討した代替案

| 案 | 採らなかった理由 |
|----|----------------|
| 1件の操作も `SELECT … FOR UPDATE` で行をロックしてから更新する | 条件付きの更新1文で足りる。ロックの往復が減り、Workers の時間も短い。また、ロックだけでは「画面を開いた後に中身が変わった」ことは分からず、結局 版の比較が要る |
| 状態だけを条件にする（`WHERE status = ?`） | 状態が同じまま金額などが直されたとき（MONEY-F-006/AC-5）を見分けられない |
| 後勝ち（条件を付けずに更新する） | 父母が同時に「払った」を押すと経過が2回残り、直した後の金額を見ずに払ったことになる |

## 結果（トレードオフ）

- 良くなること: 同時の操作で記録が食い違わない。DB との往復が少なく、ロックの待ちが無い
- 悪くなること・受け入れたリスク: 後から押した人は 409 を受けて、画面を開き直す手間がかかる（家族4人の規模では、まれ）。すべての更新で `version` を1増やすことを守る必要がある（忘れると変更を見落とす）。まとめて払ったでは `FOR UPDATE` を使うので、Hyperdrive の上でトランザクションが同じ接続で行われることを前提にする（spec 002 の T-2 で確かめる）
