# ADR-0007: 請求の当事者を members の ID で表し、「家庭」を NULL で表す

- 状態: 採用
- 日付: 2026-10-04
- 関連する spec: specs/002-money
- 置き換えた ADR: —
- 置き換えられた ADR: —

## 背景

お金（spec 002）では、請求する側・請求先・精算の払う側・受け取る側といった「当事者」に、家族の1人だけでなく「家庭」（父母を1つにまとめた相手）がなる。「家庭」は父母のどちらからでも操作でき、経過には実際に操作した家族を残す。

`members` は Supabase Auth の利用者と1対1の表で、ログインする家族4人だけが入っている（AUTH-F-001）。当事者は家族4人と「家庭」の5つで、増える見込みは無い。今後の車・ご飯の機能でも「家庭」が出てくる可能性があり、そのときの前例になる。

## 決定

- 当事者の列（`bills.from_member_id`・`bills.to_member_id`・`settlements.payer_member_id`・`settlements.receiver_member_id`）は `members.id` を指す外部キーにし、「家庭」は NULL で表す
- DB の CHECK で、両方が NULL にならない（「家庭」から「家庭」は無い）、両方が同じ家族にならない（自分に請求しない）を守る
- `members` を指す外部キーは、どれも `ON DELETE RESTRICT` にする。お金の記録がある家族の行は消さず、登録を外すときは `auth_user_id` を NULL にする（spec 002 tasks.md D-5）
- 「家庭」の名義は親だけが使える、「家庭」の請求先は息子だけ、といった `is_parent` を見る規則は API（`apps/api/src/money/`）で守る
- 関係者の判定は「当事者が自分」または「自分が親で、当事者のどちらかが NULL」で行い、一覧はこの条件を SQL の WHERE に入れる

## 検討した代替案

| 案 | 採らなかった理由 |
|----|----------------|
| 「家庭」を `members` の1行として登録する | `members` は Supabase Auth の利用者と1対1で、ログインする人の表。ログインしない行を混ぜると、家族の照合・登録の手順・立場の列の意味が崩れる |
| 当事者の表（`parties`）を別に作り、家族4人ぶん＋「家庭」を入れる | 当事者は5つで増えない。表を1つ増やすほどの得が無い。NULL＝家庭の表し方で、制約と関係者の判定が書ける |

## 結果（トレードオフ）

- 良くなること: 表を増やさずに済み、外部キーで家族の実在を DB が守る。関係者の判定が単純な WHERE で書ける
- 悪くなること・受け入れたリスク: NULL に「家庭」という意味を持たせるので、SQL を書くときに `= NULL` ではなく `IS NULL` を使うなどの注意が要る。「家庭」の名義の規則は DB の制約では守れず、API のテストで守る。家族の行を消せなくなる（登録を外すのは `auth_user_id` を NULL にする手順で行う）
