## 1. 要求の材料（→ /product-vision）

> vision の各章は、以下の事実をもとにオーナーへの質問で埋める。**ここにあるのは事実と発言だけ**で、課題・ゴールの ID 付けや言い回しは vision 作成時に決める。

### 1.1 利用者と前提（事実）

| 項目 | 内容 |
|---|---|
| 利用者 | 家族4人（父・母・息子2人）。人数は固定 |
| オーナー | せいご（息子の一人）。アプリの管理者 |
| 端末 | 4人とも Android スマートフォン。4人とも Google アカウントを持っている |
| 使い方 | スマホが主。PCからも使えるようにする |

### 1.2 今の運用と困りごと（オーナーの発言から）

| 領域 | 今の運用 | 困りごと・望み |
|---|---|---|
| ご飯を作る人 | 基本的に母が作っている。母の都合で作れないときは、母が息子一人ひとりに個別に伝えている | この連絡をアプリ上で完結させたい |
| ご飯のいる・いらない | （詳細未聴取） | 朝・昼・夕ごとに、誰の分が要るかを把握したい |
| 車 | 車は1台を家族で共有 | いつ誰が使うかを管理したい。予定の調整は家族が話し合って行う（アプリの外） |
| お金 | ①誰かが立て替えたお金を特定の個人に請求する　②医療費など親から補助されるお金を息子が親に請求する | 請求と支払いの行き違い（払った／もらっていない）を防ぎたい |

### 1.3 vision 作成時に質問で埋めるもの（未聴取）

- 各領域の「今のやり方で何が起きているか」の具体（車：予定のぶつかり方、お金：行き違いの実例など）
- 家族それぞれにとってのゴールと、成功をどう判断するか（成功指標）
- ペルソナ：両親の技術スキル、利用頻度・場面
- 利害関係者の期待（家族それぞれ）

### 1.4 オーナーが示した方針（vision の非目標・背景に効くもの）

- 完全無料の範囲で作り、運用する
- お金そのもののやり取り（決済）はアプリの範囲外。記録だけを扱う
- 予定の調整（車の取り合いなど）は人間同士で行い、アプリは先着で記録するだけ
- 将来ネイティブアプリへ移行する可能性がある（だからフロントとAPIを分ける）

## 2. 機能ごとの決定事項（→ /spec-new）

### 2.1 共通：アカウント・認証・権限

| 項目 | 決定 |
|---|---|
| ログイン方式 | **Googleログイン**（Supabase Auth） |
| アカウント作成 | 一般公開のサインアップは無効。管理者が家族4人のメールアドレスを事前登録する（初期は Supabase の管理画面から手作業で可） |
| ログイン状態の維持 | **一度ログインしたら使い続けられることがとても重要**。Android Chrome では保存領域が自動削除されないため、PWA でなくても維持できる（家族が iPhone に替えたら要再検討：Safari は7日間未訪問でストレージを消す） |
| ロール | **管理者**（せいご）。現時点で管理者だけの機能はないが、将来のためロールとして残す |
| 立場（属性） | **親**（父・母）：「家庭」宛ての請求に対応できる。**料理担当**（現在は母）：「作れない」を登録できる |
| 権限・立場の変更 | **固定の設定**。変更する画面は作らない。「ロール標準＋個人ごとの上書き」の権限モデルは採用しない |
| 日付の基準 | 画面・API・DB の日付の区切りはすべて**日本時間** |

### 2.2 車の予約

| 項目 | 決定 |
|---|---|
| 台数 | 現在1台。車は**誰でも登録できる** |
| 車の削除 | 予約の履歴がある車は削除できず、「使わない」状態にできる（新規予約の選択肢から外れ、履歴は残る）。履歴がない車は削除できる |
| 予約の単位 | 開始日時〜終了日時 |
| 重複 | 同じ車で時間が重なる予約は、**先に入れた方を優先し、後からの登録はエラー**にする（DBの制約で防ぐ） |
| 変更・取消 | 予約した本人だけ |
| 閲覧 | 全員が全員の予約を見られる |
| 付加情報 | 行き先・メモ（任意） |
| 履歴 | 過去の予約は残し、見られる |
| 予約なしの利用 | 直前に予約を入れてもらう運用で足りる（機能は作らない） |

### 2.3 お金の請求

| 項目 | 決定 |
|---|---|
| 使い道 | ①立て替えたお金を特定の個人に請求　②親から補助されるお金（医療費など）を息子が請求 |
| 項目 | 金額・カテゴリー・請求先・件名／メモ・発生日 |
| 請求先 | 特定の個人、または**「家庭」＝親（父・母のどちらか）が対応する請求先** |
| 金額 | 補助の範囲は請求する側が考慮して金額を決める。「かかった額」と「請求額」は区別しない |
| 状態 | 請求中 → 支払済 → 確認済。加えて**取消**（請求した側）と**差し戻し**（請求された側。理由を書いて戻す） |
| 閲覧 | **自分が関係する請求だけ**見られる。「家庭」宛ては父母とも関係者。**管理者も例外なし** |
| 決済 | アプリの範囲外（記録のみ） |

### 2.4 請求のカテゴリー

| 操作 | 決定 |
|---|---|
| 追加 | 誰でもできる |
| 削除 | 誰でもできる。ただし**そのカテゴリーを使っている請求が1件でもあれば削除できない**。1件もなければ削除できる |
| 名前の変更 | できない（新しく追加して古いほうを削除する） |

### 2.5 ご飯のいる・いらない

| 項目 | 決定 |
|---|---|
| 対象 | 朝・昼・夕の3食 |
| 状態 | いる／いらない／未入力 を区別して表示する |
| 入力者 | 本人の分だけ |
| まとめて入力 | **採用**（例：その日の3食をまとめて、数日分をまとめて） |
| 締切 | なし |
| 過去の分 | **いつでも変更できる**（変更を止める仕組みは作らない） |
| 入力できる範囲 | 無期限（何日先でも入力できる） |
| 閲覧 | 全員が全員の分を見られる |

### 2.6 ご飯を作れない日（と通知）

| 項目 | 決定 |
|---|---|
| 機能の意味 | 料理担当が「作れない食事」を登録し、家族に知らせる |
| 既定 | 何も登録しなければ「作る」とみなす。作れないときだけ登録する |
| 入力者 | 料理担当（現在は母）。「母」に固定せず立場として持つ |
| 単位 | 1日の朝・昼・夕ごと。まとめて入力もできる |
| 付加情報 | 任意のメモ（例：「外出のため夕食は各自」） |
| ご飯画面への反映 | 作れない食事はご飯の画面で目立つように表示する。家族の「いる・いらない」は自動では変えない |
| 入力できる範囲 | 無期限（何日先でも） |
| 通知 | 「作れない」の**登録・変更時に Web プッシュで家族に知らせる（Scope 1 に含める）**。これ以外の通知は Scope 1 では作らない |

### 2.7 端末・形態

| 項目 | 決定 |
|---|---|
| 画面 | スマホ優先、PC 対応（レスポンシブ） |
| PWA | **Scope 1 から対応**（ホーム画面に追加して開ける） |

## 3. スコープ

### 3.1 後回し（将来の spec 候補）

| 項目 | 理由・メモ |
|---|---|
| 割り勘 | 一旦なくす。後々追加するかも（入れる場合は請求の中に「払う人ごとの行」ができる） |
| 相殺（差し引き精算） | 仕組みが複雑になるため。後々追加するかも |
| 請求の集計（年別・カテゴリー別。医療費控除など） | Scope 1 に含めない。後々追加するかも |
| ご飯の繰り返し入力（「毎週水曜はいらない」など） | Scope 1 に含めない。後々追加するかも |
| 「作れない」以外の通知（締切・請求・車の予約など） | 一旦なし。Web プッシュの仕組みは Scope 1 で入るので追加は容易 |
| バックアップ | 取れなくても大丈夫。取るなら GitHub Actions で dump → R2 など |
| 管理者だけの機能 | 今は無いが、ロールは残してある |

### 3.2 やらない

| 項目 | 理由 |
|---|---|
| 決済（お金の実際のやり取り） | アプリの範囲外。手渡し・PayPay 等で行う |
| レシート・領収書の画像 | 誰も面倒がってやらないため |
| 来客分のご飯 | 実装しない |
| 予定の調整（車の取り合いの解決など） | 人間同士で行う |
| 権限・立場を変える画面 | 4人固定のため、固定の設定で足りる |
| 請求の「かかった額」と「請求額」の区別 | 請求する側が補助範囲を考慮して金額を決めるため |
| Google Play での配布 | 開発者登録に $25 かかり、完全無料の制約に反する。配布は PWA（必要なら APK の直接配布） |

## 4. 技術・アーキテクチャ（→ 基盤 spec／architecture.md／ADR）

### 4.1 制約

- **完全無料の範囲で完結する**。クレジットカードの登録は可（ただし超過分が課金されるサービスは使い方に注意）。Scope 1 の構成（Workers Free・Pages・Supabase Free）には自動課金されるものが無く、カード登録は実質不要の見込み
- フロントエンドとバックエンドは完全に分離する
- DB を使う
- 独自ドメインは使わない（`*.pages.dev` / `*.workers.dev`）
- GitHub Student Developer Pack の特典は使ってよい。ただし卒業後も無料で続けられるよう、それに依存しない選択を優先する

### 4.2 技術スタック

| 役割 | 採用 | 置き場所 |
|---|---|---|
| フロントエンド | **Vite ＋ React（TypeScript）**、SPA、PWA | Cloudflare Pages |
| バックエンド API | Hono（TypeScript） | Cloudflare Workers |
| 認証 | Supabase Auth（Google ログイン） | Supabase |
| DB | Supabase Postgres | Supabase |
| DB 接続 | Hyperdrive（第一候補。要検証）。代替は Supavisor のトランザクションモード（`prepare: false` が必要） | — |
| ORM・マイグレーション | Drizzle ／ Drizzle Kit に一本化 | — |
| 入力検証 | Zod | — |
| API の型付け | Hono RPC（`hc`） | — |
| パッケージマネージャー | pnpm（corepack で有効化） | — |
| テスト | Vitest | — |
| エラー監視 | Sentry の一般無料プラン（Developer）。学生特典には依存しない | — |
| 通知 | Web プッシュ（VAPID 鍵は Workers の secret） | — |
| ソース管理・CI | GitHub / GitHub Actions | GitHub |

### 4.3 アーキテクチャの原則（旧 CLAUDE.md から継続）

1. フロントは `supabase-js` をログイン・ログアウト・セッション管理にだけ使う。データの読み書きには使わない
2. データの読み書きはすべて Hono API を経由する
3. API 呼び出しは Supabase のアクセストークンを `Authorization: Bearer` で送る。Cookie は使わない（ネイティブアプリからも同じ方式で使える）
4. API は Supabase の JWT を検証し、認可は API 側で行う。フロントのボタンの出し分けは見た目のためだけ
5. Supabase の Data API（PostgREST）経由の直接アクセスは塞ぐ（無効化、または全テーブル RLS 有効・ポリシーなし）
6. サービスロールキー（secret key）と DB 接続情報は Workers の secret にだけ置く。フロントに置くのは Supabase の URL と公開キーだけ
7. 一般公開のサインアップは無効。家族のアカウントは管理者が事前登録する
8. CORS で許可するのは、自分のフロントのオリジン、プレビュー用 URL（開発環境のみ）、開発用の localhost だけ
9. 画面以外の部分（API の型・入力検証・請求の状態遷移などのルール）は `packages/` に置き、将来のネイティブアプリと共有できるようにする

### 4.4 リポジトリ構成と命名

GitHub リポジトリは `stylus` 1つ（private、monorepo）。

```
stylus/
├─ apps/
│  ├─ web/        フロントエンド（Vite + React）→ Cloudflare Pages
│  └─ api/        バックエンド（Hono）→ Cloudflare Workers
├─ packages/      フロントと API で共有するもの（型・スキーマ・ルール）
├─ docs/          仕様駆動ワークフローの文書（/spec-setup が作る）
├─ .github/workflows/
└─ CLAUDE.md
```

- `apps/web` から `apps/api` の実行コードを import しない（`import type` のみ可）
- 共有したいものは `packages/` に切り出す

| 対象 | 本番 | 開発 |
|---|---|---|
| Cloudflare Pages | `stylus`（本番ブランチ） | 同プロジェクトのプレビューデプロイ（開発用 API につなぐ） |
| Cloudflare Worker | `stylus-api` | `stylus-api-dev` |
| Supabase プロジェクト | `stylus` | `stylus-dev` |

- Supabase の無料プランで同時に動かせるプロジェクトは2つまで → 本番・開発でちょうど使い切る
- `stylus.pages.dev` が取られていたら、実際に割り当てられた URL を CORS と Supabase Auth（Site URL・Redirect URLs）に反映する

### 4.5 無料枠の制約と運用上必須のこと

| 対象 | 制約 | 対応 |
|---|---|---|
| Workers（無料） | 1日10万リクエスト、CPU 時間 10ms/リクエスト | 重い処理を Workers でしない。パスワード処理は持たない（Google ログイン） |
| Supabase（無料） | 7日間アクセスが無いと停止 | Workers Cron で**本番・開発の両方**に毎日アクセスする（何が「アクセス」と数えられるかは要検証） |
| Supabase（無料） | バックアップ機能が無い | Scope 1 では取らない |
| 日時 | Workers の Cron は UTC で動く | 日付の区切りは日本時間に揃える（2.1） |

### 4.6 ローカル開発環境

| 項目 | 決定 |
|---|---|
| 方式 | **Windows に直接構築**（WSL・Dev Container は使わない） |
| 既存ツール | Node.js v24、git、Python 3.14（`spec-check` 用）、Docker が導入済み。追加は pnpm のみ |
| 開発用 DB | クラウドの `stylus-dev` に直接つなぐ。ローカルの Supabase が必要になったら既存の Docker を使う |
| 改行コード | `.gitattributes` で LF に揃える（CI は Linux） |
| スクリプト | package.json のスクリプトは OS に依存しない書き方にする |
| Claude Code | 現在の Windows 環境（デスクトップアプリ、`~/.claude/skills`）のまま使う |

### 4.7 ADR にする候補

| 候補 | 決定 | 理由 |
|---|---|---|
| フロントとバックエンドの完全分離 | 分離する | 拡張性（将来のネイティブアプリ移行）、役割分離による堅牢さ |
| フロントエンドのフレームワーク | Vite ＋ React（Next.js 静的出力から変更） | 静的出力の Next.js は機能をほぼ使えず制約だけが残る。静的ホスティングに素直。フレームワークへのこだわりは無い。Expo は Web 版の完成度と学習量で不利 |
| ログイン方式 | Google ログイン＋事前登録 | 全員 Google アカウントを持つ。メール送信（独自 SMTP）が不要になり、独自ドメインなしの制約と両立する |
| 通知 | Scope 1 は「作れない」だけ Web プッシュ | 母の個別連絡を置き換えるには通知が不可欠。全員 Android でコストがかからない |
| 配布形態 | PWA | Google Play は $25 かかる。Android なら PWA でネイティブに近い体験になる |
| ローカル環境 | Windows に直接構築 | 必要なツールが既に揃っており、スキル・Claude Code をそのまま使える |
| 認証と DB | Supabase Auth ＋ Postgres、Data API は塞ぎ Hono 経由 | 旧 CLAUDE.md の決定。認可を API に集約する |

## 5. 実物で確かめる項目（→ 基盤 spec）

| # | 確かめること | うまくいかなかったときの代替 |
|---|---|---|
| V-1 | サインアップ無効のまま、事前登録したユーザーが Google ログインでき、同じメールのユーザーに紐づくか | サインアップは許可し API 側で許可リスト外を 403／Supabase Auth の「ユーザー作成前」フックで許可リスト外を拒否 |
| V-2 | Supabase の休止対策として、Workers Cron からの DB アクセスが「アクセス」と数えられるか（Data API を塞いだ状態で） | Data API の一部だけ開けて叩く、など |
| V-3 | Workers Free で Hyperdrive から Supabase に接続できるか | Supavisor トランザクションモード（`prepare: false`） |
| V-4 | Workers の CPU 10ms 以内で Web プッシュ（暗号化・VAPID 署名）を送れるか | 送信処理の分割、別の送信経路の検討 |
| V-5 | Cloudflare Pages の `stylus` が使えるか | 割り当てられた URL を CORS・Supabase Auth に反映 |
